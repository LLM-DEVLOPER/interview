### X. 设计模式

#### A. 设计模式基础与原则

##### 1. 什么是设计模式？有什么好处？ ★★★★☆

什么是设计模式？

设计模式（Design Pattern）是在软件开发过程中，针对特定问题或场景，经过反复实践、总结和提炼出的一套可复用的、行之有效的解决方案。它不是一个具体的类或代码，而是一种解决问题的思想和模式。

**有什么好处？**

1. **提高代码的可复用性：** 模式是可复用的，可以应用于不同的项目中。
2. **提高代码的可读性和可维护性：** 使用通用的设计模式，能让其他开发者更容易理解你的代码意图，便于后续的维护和扩展。
3. **提升系统健壮性：** 设计模式通常是经过千锤百百炼的成熟方案，遵循它们可以使系统架构更稳定、更可靠。
4. **实现高内聚、低耦合：** 设计模式的核心目标之一就是解耦，让模块间的依赖关系更清晰。
5. **是工程师之间沟通的“行话”：** 说“这里用一个策略模式”，比详细描述实现细节要高效得多。

##### 2. 设计模式的7大基本原则有哪些？ ★★★★☆

设计模式遵循七大基本原则，它们是高质量软件设计的基石，常被缩写为 **SOLID** + **LKP** + **CRP**。

1. **单一职责原则 (Single Responsibility Principle - SRP):**
   - 一个类只应该负责一项职责。即，引起一个类变化的原因应该只有一个。
2. **开闭原则 (Open/Closed Principle - OCP):**
   - 软件实体（类、模块、函数等）应该对**扩展开放**，对**修改关闭**。即，在不修改原有代码的情况下，通过增加新代码来扩展功能。
3. **里氏替换原则 (Liskov Substitution Principle - LSP):**
   - 所有引用基类的地方，必须能透明地使用其子类的对象。通俗讲，子类可以扩展父类的功能，但不能改变父类原有的功能。
4. **接口隔离原则 (Interface Segregation Principle - ISP):**
   - 客户端不应该依赖它不需要的接口。一个类对另一个类的依赖应该建立在最小的接口上。即，接口要小而专，不要设计臃肿的接口。
5. **依赖倒置原则 (Dependence Inversion Principle - DIP):**
   - 高层模块不应该依赖低层模块，两者都应该依赖其抽象。抽象不应该依赖细节，细节应该依赖抽象。核心思想是**面向接口编程**。
6. **迪米特法则 (Law of Demeter - LoD / 最少知识原则):**
   - 一个对象应该对其他对象保持最少的了解。即，一个类应该只与它的直接朋友（成员变量、方法参数、方法返回值等）交谈，不与“陌生人”说话。
7. **组合/聚合复用原则 (Composite/Aggregate Reuse Principle - CARP):**
   - 尽量使用组合/聚合的方式，而不是使用继承来达到复用的目的。组合比继承更灵活。

##### 3. 在工作中是如何使用设计模式的？ ★★★★☆

这是一个开放性问题，需要结合具体项目经验来回答。

回答示例：

“在我的工作中，设计模式是解决日常开发问题的常用工具。比如：

- **策略模式：** 在一个支付系统中，我们需要支持多种支付方式（如微信支付、支付宝支付、银行卡支付）。我使用了策略模式，将每种支付方式的逻辑封装成一个独立的策略类，它们都实现同一个支付接口。这样，当需要新增一种支付方式时，只需增加一个新的策略类，而无需修改原有的业务代码，完全符合开闭原则。
- **工厂模式：** 在处理不同类型消息的解析时，我使用了工厂模式。根据消息的类型（`type`字段），工厂类会创建出对应类型的消息解析器（`MessageParser`），避免了在业务代码中出现大量的`if-else`或`switch-case`来判断和创建对象。
- **单例模式：** 对于系统中的配置文件读取类、数据库连接池等只需要一个实例的重量级对象，我使用了单例模式来确保其全局唯一，避免了资源的浪费。
- **模板方法模式：** 在处理一个有固定流程但部分步骤有差异的业务时，比如数据导出，我定义了一个抽象的导出模板类，封装了“读取数据 -> 处理数据 -> 生成文件”的骨干流程，而将“处理数据”这个易变的步骤作为抽象方法，交由子类去实现，提高了代码的复用性。”

##### 4. 使用哪种设计模式可以提高代码可维护性？ ★★★☆☆

几乎所有设计模式的最终目的都包含提高可维护性。其中一些尤其突出：

1. **策略模式 (Strategy):** 将易变的算法或行为封装起来，使它们可以相互替换。当业务规则频繁变化时，使用策略模式可以避免大量的`if-else`，使得新增和修改逻辑变得非常容易。
2. **模板方法模式 (Template Method):** 定义了一个操作中的算法骨架，而将一些步骤延迟到子类中。它固定了核心流程，让子类只关注差异化的实现，使得代码结构清晰，易于维护。
3. **状态模式 (State):** 当一个对象的行为取决于它的状态，并且它在运行时根据状态改变它的行为时，使用状态模式。它将与特定状态相关的行为局部化，并且使得状态的转换显式化，避免了复杂的条件判断，提高了可维护性。
4. **工厂模式 (Factory Method / Abstract Factory):** 将对象的创建过程与使用过程解耦，当需要更换或增加新的产品实现时，只需修改工厂或增加新工厂，而无需修改客户端代码。

##### 5. 使用哪种设计模式可以提高代码的复用性？ ★★★☆☆

1. **模板方法模式 (Template Method):** 这是**为复用而生**的设计模式。它将算法中不变的部分（骨架）提取到父类中，实现了通用逻辑的复用，而将可变的部分留给子类实现。
2. **策略模式 (Strategy):** 将可复用的算法或行为封装成独立的策略类，这些策略类可以在不同的上下文中被复用。
3. **建造者模式 (Builder):** 将一个复杂对象的构建过程与其表示分离。相同的构建过程可以用于创建不同的表示（产品），实现了构建逻辑的复用。
4. **原型模式 (Prototype):** 通过复制一个已有的实例来创建新的实例，当创建新对象的成本较大时，通过原型模式可以复用已有对象的状态。

#### B. 创建型设计模式

##### 1. 单例模式的多种写法？如何破坏单例模式？为什么说枚举是实现单例最好的方式？不使用锁如何实现线程安全的单例？ ★★★★★

**单例模式的多种写法：**

1. **饿汉式 (Eager Initialization):**

   ```
   public class Singleton {
       private static final Singleton INSTANCE = new Singleton();
       private Singleton() {}
       public static Singleton getInstance() {
           return INSTANCE;
       }
   }
   ```

   - **优点：** 写法简单，线程安全（类加载时就已创建）。
   - **缺点：** 不支持懒加载，可能造成资源浪费。

2. **懒汉式 (Lazy Initialization) - 线程不安全:**

   ```
   public class Singleton {
       private static Singleton instance;
       private Singleton() {}
       public static Singleton getInstance() {
           if (instance == null) {
               instance = new Singleton();
           }
           return instance;
       }
   }
   ```

3. **懒汉式 - 同步方法 (线程安全):**

   ```
   public static synchronized Singleton getInstance() { ... }
   ```

   - **缺点：** 性能差，每次获取实例都需要加锁。

4. **双重检查锁定 (Double-Checked Locking - DCL):**

   ```
   public class Singleton {
       private static volatile Singleton instance; // volatile是关键
       private Singleton() {}
       public static Singleton getInstance() {
           if (instance == null) {
               synchronized (Singleton.class) {
                   if (instance == null) {
                       instance = new Singleton();
                   }
               }
           }
           return instance;
       }
   }
   ```

   - **优点：** 兼顾了懒加载和性能。

5. **静态内部类 (Static Inner Class) (推荐):**

   ```
   public class Singleton {
       private Singleton() {}
       private static class SingletonHolder {
           private static final Singleton INSTANCE = new Singleton();
       }
       public static Singleton getInstance() {
           return SingletonHolder.INSTANCE;
       }
   }
   ```

   - **优点：** 实现了懒加载，且由JVM保证线程安全，写法优雅。

6. **枚举 (Enum) (最佳方式):**

   ```
   public enum Singleton {
       INSTANCE;
       public void doSomething() { ... }
   }
   ```

**如何破坏单例模式？**

- **反射 (Reflection):** 可以通过反射调用私有的构造方法来创建新的实例。
- **序列化 (Serialization):** 如果单例类实现了`Serializable`接口，反序列化时会创建一个新的实例。

**为什么说枚举是实现单例最好的方式？**

1. **写法最简单。**
2. **由JVM保证线程安全**，无需任何同步代码。
3. **天然防止反射和反序列化攻击。** JVM在底层实现上，严格禁止通过反射和反序列化来创建枚举的实例。

不使用锁如何实现线程安全的单例？

静态内部类的方式就实现了不使用显式锁（synchronized）的线程安全。

- **原理：** 它的线程安全是由**JVM的类加载机制**来保证的。当`getInstance()`方法第一次被调用时，才会触发`SingletonHolder`这个静态内部类的加载和初始化。而JVM保证一个类的初始化过程在多线程环境下是正确同步的，即只会被执行一次。

##### 2. 三种工厂模式的区别和特点？ ★★★★★

1. **简单工厂模式 (Simple Factory):**
   - **定义：** 提供一个专门的工厂类，根据传入的参数来决定创建哪一种产品类的实例。它**不属于**23种GoF设计模式之一，更像是一种编程习惯。
   - **核心：** 一个工厂类，一个`switch`或`if-else`判断。
   - **缺点：** 违背了开闭原则。当需要增加新产品时，必须修改工厂类的判断逻辑。
2. **工厂方法模式 (Factory Method):**
   - **定义：** 定义一个用于创建对象的接口，但让**子类**来决定要实例化哪一个类。工厂方法使一个类的实例化延迟到其子类。
   - **核心：** 定义一个**抽象工厂**和**抽象产品**，每一种具体产品都对应一个**具体工厂**。
   - **优点：** 完美符合开闭原则。增加新产品时，只需增加新的具体产品类和具体工厂类即可，无需修改现有代码。
   - **缺点：** 每增加一个产品，就需要增加一个对应的工厂类，导致类的数量成倍增加。
3. **抽象工厂模式 (Abstract Factory):**
   - **定义：** 提供一个接口，用于创建**一系列相关或相互依赖的对象**（一个产品族），而无需指定它们具体的类。
   - **核心：** 围绕一个“产品族”来创建。例如，一个换肤功能，有“春天主题工厂”和“夏天主题工厂”，前者能创建出“春天按钮”、“春天文本框”，后者能创建出“夏天按钮”、“夏天文本框”。
   - **优点：** 隔离了具体类的生成，便于切换整个产品族。
   - **缺点：** 扩展新的产品等级结构非常困难。例如，如果要增加一个新的“滚动条”产品，那么所有的工厂接口和实现类都需要修改。

#### C. 结构型设计模式

##### 1. 什么是不可变模式，有哪些应用？ ★★★★☆

什么是不可变模式 (Immutable Pattern)？

不可变模式是指一个对象在被创建之后，其内部状态（成员变量）就永远不能被改变。任何对该对象的修改操作，都会返回一个新的对象，而原对象保持不变。

**实现不可变类的规则：**

1. 类使用`final`修饰，防止被继承。
2. 所有成员变量都使用`private final`修饰。
3. 不提供任何`setter`方法。
4. 构造方法中对所有字段进行初始化。
5. 如果成员变量是可变对象（如`List`, `Date`），在构造时进行深拷贝，在getter方法中返回其拷贝，防止外部修改。

**有哪些应用？**

- **`java.lang.String`:** 最经典的不可变对象。任何对String的操作（如`concat`, `substring`）都会返回一个新的String对象。
- **JDK中的包装类：** `Integer`, `Long`, `Double`等。
- **`java.time`包下的类：** `LocalDate`, `LocalDateTime`等都是不可变的。
- **优点：**
  - **线程安全：** 不可变对象天然是线程安全的，可以在多线程环境下安全地共享，无需任何同步措施。
  - **可作为缓存的Key：** 因为其`hashCode()`是固定的，非常适合用作`HashMap`的键。

##### 2. 什么是享元模式，有哪些具体应用？ ★★★☆☆

什么是享元模式 (Flyweight Pattern)？

享元模式是一种结构型设计模式，它旨在通过共享技术，来有效地支持大量细粒度对象的复用。

核心思想：

将一个对象的状态分为两部分：

- **内部状态 (Intrinsic State):** 可以被共享的、不随外部环境改变的部分。
- **外部状态 (Extrinsic State):** 不可以被共享的、随外部环境改变的部分。

享元模式会创建一个“享元工厂”，将所有具有相同内部状态的对象缓存起来。当客户端需要一个对象时，工厂会先查找缓存，如果存在则直接返回共享的实例，如果不存在则创建一个新的实例并放入缓存。外部状态则在使用时由客户端传入。

**有哪些具体应用？**

- **`java.lang.Integer.valueOf()`:** 当你调用`Integer.valueOf(10)`时，对于-128到127之间的整数，它会返回一个缓存好的、共享的`Integer`对象，而不是每次都`new`一个新的。这就是一个享元模式的应用。`String`的字符串常量池也是同理。
- **数据库连接池/线程池：** 连接和线程都是重量级资源，创建和销毁成本高。连接池和线程池将这些可复用的对象（其内部状态是可共享的）缓存起来，供多个任务共享使用。

##### 3. String的设计，用到了哪些设计模式？ ★★★★★

Java的`String`类的设计是面试中的高频考点，它巧妙地运用了多种设计模式。

1. **不可变模式 (Immutable Pattern):**
   - 这是`String`最核心的特性。`String`对象一旦被创建，其内部的字符数组（`value`）就不能被改变。所有看似修改`String`的方法，实际上都是返回一个新的`String`对象。
   - **好处：** 保证了线程安全，并使其可以安全地用作`HashMap`的键。
2. **享元模式 (Flyweight Pattern):**
   - 体现在**字符串常量池（String Pool）**上。当我们使用字面量（如`String s = "abc";`）创建字符串时，JVM会先在常量池中查找是否存在值为`"abc"`的字符串。如果存在，则直接返回其引用；如果不存在，则在常量池中创建一个新的实例。
   - **好处：** 极大地复用了字符串对象，节省了内存。
3. **建造者模式 (Builder Pattern) / 适配器模式 (Adapter Pattern):**
   - `StringBuilder`和`StringBuffer`可以看作是`String`的建造者。当需要进行大量的字符串拼接操作时，我们使用它们来构建最终的字符串，这比使用`+`号连接性能高得多。
   - 同时，它们也扮演了适配器的角色，将可变的字符串操作接口，适配给了最终不可变的`String`对象。

##### 4. 什么是代理模式，有哪些应用？ ★★★★★

什么是代理模式 (Proxy Pattern)？

代理模式是指为其他对象提供一种代理以控制对这个对象的访问。代理对象在客户端和目标对象之间起到了一个中介的作用，可以在不改变目标对象代码的情况下，增加额外的功能或控制。

**代理模式的分类：**

- **静态代理：** 代理类和目标类的关系在编译时就已确定。需要为每个目标类都手动编写一个代理类。
- **动态代理：** 在运行时动态地生成代理对象。
  - **JDK动态代理：** 基于**接口**实现。代理的类必须实现一个或多个接口。
  - **CGLIB动态代理：** 基于**继承**实现。可以代理没有实现接口的类。

有哪些应用？

代理模式的应用极其广泛，是许多框架的底层核心。

- **Spring AOP (面向切面编程):** Spring AOP的实现就是基于动态代理。它通过为目标Bean创建代理对象，在方法执行前后织入通知（Advice），从而实现了日志、事务、权限控制等横切关注点的功能。
- **RPC框架 (远程过程调用):** 客户端调用一个远程服务的接口时，框架会为其生成一个代理对象。这个代理对象负责封装方法调用信息、进行网络通信，让调用者感觉就像在调用本地方法一样。
- **数据库连接池：** 连接池返回给应用的`Connection`对象，通常也是一个代理对象，它会拦截`close()`方法，不是真正关闭物理连接，而是将其归还到池中。
- **MyBatis的Mapper接口：** MyBatis为Mapper接口生成的实现类，就是一个代理对象。

##### 5. 请简述MVC模式的思想？ ★★★★☆

MVC (Model-View-Controller) 是一种经典的软件设计模式，主要用于构建用户界面。它的核心思想是**将应用程序的输入、处理和输出进行分离**，即将业务逻辑、数据和界面显示进行解耦。

**MVC的三个核心组件：**

1. **Model (模型):**
   - **职责：** 负责应用程序的**业务逻辑**和**数据**。它封装了应用的状态和业务规则，并负责与数据持久层（如数据库）进行交互。
   - **特点：** Model是独立于视图和控制器的，它不知道自己如何被展示。
2. **View (视图):**
   - **职责：** 负责**数据的展示**和**用户界面的渲染**。它从Model中获取数据，并将其呈现给用户。
   - **特点：** View是被动的，它只负责显示，不包含任何业务逻辑。
3. **Controller (控制器):**
   - **职责：** 扮演**协调者**的角色。它接收用户的输入（如HTTP请求），调用相应的Model来处理业务逻辑，然后选择一个合适的View来渲染Model的返回结果，并最终将View呈现给用户。
   - **特点：** Controller是Model和View之间的桥梁。

工作流程：

用户输入 -> Controller -> Model -> Controller -> View -> 用户界面

通过这种分离，使得系统的各个部分可以独立地进行开发和修改，提高了代码的可维护性和可复用性。

#### D. 行为型设计模式

##### 1. 什么是责任链模式，有哪些应用？ ★★★★☆

什么是责任链模式 (Chain of Responsibility Pattern)？

责任链模式是一种行为设计模式，它旨在避免请求的发送者和接收者之间的耦合。它将多个能够处理请求的对象连接成一条链，然后将请求沿着这条链进行传递，直到有一个对象处理它为止。

**核心思想：**

- 每个处理器（Handler）都持有对下一个处理器的引用。
- 当一个请求到来时，处理器会判断自己是否能处理该请求。
- 如果能处理，就处理它；如果不能，就将请求**传递给链中的下一个处理器**。
- 客户端只需将请求发送给链的第一个处理器，而无需关心请求最终由谁处理。

**有哪些应用？**

- **Java Web中的Servlet过滤器 (Filter):** 一个HTTP请求会依次通过一个Filter链，每个Filter都可以对请求进行处理（如编码转换、权限检查），然后决定是放行给下一个Filter还是直接返回响应。
- **MyBatis的插件机制 (Interceptor):** MyBatis的插件通过责任链模式，将多个拦截器串联起来，对Executor等核心对象的调用进行层层代理和拦截。
- **Spring Security的过滤器链。**
- **异常处理机制中的`try-catch`块**，也可以看作是一种责任链。

##### 2. 什么是状态模式，有哪些应用？ ★★★☆☆

什么是状态模式 (State Pattern)？

状态模式是一种行为设计模式，它允许一个对象在其内部状态改变时，改变它的行为。从外部看，就好像这个对象的类发生了改变一样。

**核心思想：**

- 将与特定状态相关的行为，封装到一个个独立的**状态类**中。
- 上下文对象（Context）持有一个对当前状态对象的引用。
- 所有对上下文对象的请求，都被委托给当前的状态对象来处理。
- 状态类内部负责处理业务逻辑，并决定在什么条件下，将上下文对象的状态切换到下一个状态。

与if-else的区别：

它将大量的、与状态相关的if-else或switch-case判断，分散到了各个独立的状态类中，使得代码结构更清晰，更符合开闭原则。

**有哪些应用？**

- **订单状态机：** 一个订单有“待支付”、“已支付”、“待发货”、“已发货”、“已完成”、“已取消”等多种状态。每个状态下，订单允许的操作（如支付、取消、发货）是不同的。使用状态模式，可以为每个状态创建一个类，来管理其行为和状态转换。
- **工作流引擎：** 流程的审批节点（如“待审批”、“审批中”、“已驳回”、“已通过”）可以用状态模式来管理。
- **网络连接状态：** TCP连接的状态（如`ESTABLISHED`, `CLOSE_WAIT`, `TIME_WAIT`）也是一个典型的状态机。

##### 3. 策略模式和if-else相比有什么好处？ ★★★★☆

策略模式是优化大量`if-else`或`switch-case`的经典方案。

**场景：** 当一个业务的实现有多种方式（策略），并且需要根据不同的条件选择不同的方式时。

**if-else的缺点：**

- **违反开闭原则：** 每当需要增加一种新的策略时，都必须修改原有的`if-else`代码块，增加了引入Bug的风险。
- **代码臃肿，可读性差：** 如果策略很多，会形成一个非常长、难以维护的`if-else`结构。
- **复用性差：** 逻辑都耦合在一个方法里，难以复用。

**策略模式的好处：**

1. **符合开闭原则，易于扩展：**
   - 将每一种策略（算法）都封装成一个独立的**策略类**，它们实现一个共同的策略接口。
   - 当需要增加新策略时，只需增加一个新的策略类即可，完全不需要修改原有的上下文（Context）代码。
2. **代码更清晰，可维护性高：**
   - 避免了庞大的条件判断语句，每个策略的逻辑都清晰地封装在自己的类中。
3. **高复用性：**
   - 每个策略类都可以被不同的上下文复用。
4. **客户端可以自由切换策略：**
   - 可以在运行时动态地改变一个对象的行为（策略）。

##### 4. 什么是观察者模式，有哪些应用？ ★★★★☆

什么是观察者模式 (Observer Pattern)？

观察者模式定义了对象之间一种一对多（One-to-Many）的依赖关系。当一个对象（被称为主题/Subject或被观察者/Observable）的状态发生改变时，所有依赖于它的对象（被称为观察者/Observer）都会得到通知并自动更新。

**核心思想：**

- **解耦：** 它让主题和观察者之间松散耦合。主题只知道它有一系列的观察者，但不需要知道这些观察者具体是谁，做了什么。观察者也只知道自己要关注某个主题，但不知道还有哪些其他观察者。

有哪些应用？

观察者模式是实现事件驱动和消息通知机制的基础。

- **GUI事件监听：** 桌面应用中，按钮（主题）的点击事件，可以被多个监听器（观察者）监听并做出响应。
- **发布/订阅模型 (Pub/Sub):** 这是观察者模式在分布式系统中的一种体现。消息的生产者（发布者/主题）将消息发送到主题中，所有订阅了该主题的消费者（订阅者/观察者）都能收到这条消息。**Redis的Pub/Sub功能**、**消息队列（MQ）**都是其典型应用。
- **Spring框架中的事件机制 (`ApplicationEvent`):** Spring应用可以发布自定义事件，所有实现了`ApplicationListener`的Bean（观察者）都可以监听到并处理该事件。

##### 5. 什么是模板方法模式，有哪些应用？ ★★★☆☆

什么是模板方法模式 (Template Method Pattern)？

模板方法模式是一种行为设计模式，它在一个方法中定义一个算法的骨架（模板），而将一些具体的步骤延迟到子类中去实现。

**核心思想：**

- 在**抽象父类**中，定义一个`final`的**模板方法**，这个方法封装了算法的固定流程和步骤调用顺序。
- 模板方法中，会调用一些**抽象方法**或**钩子方法（Hook Method）**。
- **抽象方法**由子类必须实现，用于处理算法中可变的部分。
- **钩子方法**是父类中提供的空实现或默认实现，子类可以选择性地去覆盖（override）它，以对算法流程进行微调。

**有哪些应用？**

- **JDK中的`AbstractList`：** `AbstractList`实现了List接口中大部分通用的方法（如`indexOf`, `lastIndexOf`），但将`get(index)`和`size()`等核心方法定义为抽象的，交由其子类（如`ArrayList`, `LinkedList`）去实现。
- **Java Web中的Servlet：** `HttpServlet`的`service()`方法就是一个模板方法，它定义了处理HTTP请求的整体流程（判断请求类型是GET、POST等），然后调用`doGet()`, `doPost()`等方法，而这些方法则由我们自己编写的Servlet子类去实现。
- **Spring中的`JdbcTemplate`和各种`...Template`类：** 它们封装了资源获取、异常处理、资源释放等固定流程，而将最核心的SQL执行和结果集处理逻辑，通过回调的方式交由开发者来实现。

##### 6. 针对天气预报变化时触发用户通知和推荐行程用什么设计模式？ ★★★★☆

这是一个非常典型的**观察者模式 (Observer Pattern)** 的应用场景。

**设计分析：**

- **主题 (Subject / 被观察者):** **天气预报服务**。它的核心状态是“天气情况”。当这个状态发生变化时，需要通知所有关心它的人。
- **观察者 (Observers):**
  - **用户通知服务：** 这是一个观察者。它订阅天气预报服务，当收到天气变化的通知时，就向相关用户发送推送。
  - **行程推荐服务：** 这是另一个观察者。它也订阅天气预报服务，当收到通知（如“明天要下雨”）时，就为用户推荐室内的行程安排。

**实现流程：**

1. 定义一个`WeatherSubject`接口，包含`registerObserver`, `removeObserver`, `notifyObservers`等方法。
2. 定义一个`Observer`接口，包含一个`update(weatherInfo)`方法。
3. `WeatherForecastService`实现`WeatherSubject`接口。它内部维护一个观察者列表。
4. `UserNotificationService`和`TripRecommendationService`都实现`Observer`接口。
5. 系统初始化时，将这两个服务实例注册（`registerObserver`）到`WeatherForecastService`中。
6. 当天气预报数据更新时，`WeatherForecastService`调用自己的`notifyObservers()`方法，遍历其观察者列表，并调用每个观察者的`update()`方法，将最新的天气信息传递过去。

好处：

天气预-报服务与用户通知、行程推荐这两个业务完全解耦。未来如果需要增加一个新的功能，比如“智能窗帘控制服务”，只需再增加一个新的观察者实现即可，无需修改任何现有代码，符合开闭原则。
