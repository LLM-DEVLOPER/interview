## IV. JVM

### 1. JVM 基础概念

#### 1.1 JVM概述

##### 1. JVM是什么？ ★★★☆☆

JVM，全称Java虚拟机（Java Virtual Machine），是一个可以执行Java字节码的**抽象计算机**。

它是一种规范，定义了程序在运行时所需的环境。不同的厂商（如Oracle, Azul）可以根据这个规范提供不同的实现。JVM是Java实现“**一次编写，到处运行**”（Write Once, Run Anywhere）的关键。

##### 2. JVM与JRE、JDK的关系是什么？ ★★★☆☆

它们是层层包含的关系：**JDK > JRE > JVM**。

- **JDK (Java Development Kit)**：Java**开发工具包**。它是功能最全的SDK，面向开发者，包含了JRE以及编译器（`javac`）、调试器等开发工具。
- **JRE (Java Runtime Environment)**：Java**运行时环境**。它面向使用者，包含了JVM和Java程序运行所需的核心类库。
- **JVM (Java Virtual Machine)**：Java**虚拟机**。它是JRE的核心，负责解释和执行Java字节码。

**比喻**：如果把JVM比作发动机，那么JRE就是一辆完整的汽车（包含发动机、车轮、底盘等），而JDK则是一个汽车修理厂（不仅有完整的汽车，还有各种修理和制造工具）。

##### 3. HotSpot虚拟机是什么？ ★★★☆☆

HotSpot是目前使用最广泛的、Oracle官方的**高性能JVM实现**。我们通常所说的“JVM”在很多情况下指的就是HotSpot虚拟机。

它的名字来源于其核心技术——**热点代码探测（Hot Spot Detection）**。它能在运行时动态地识别出执行最频繁的代码（即“热点代码”），然后通过**即时编译器（JIT, Just-In-Time Compiler）**将这部分代码编译成与本地平台相关的机器码，从而极大地提升了执行效率。

##### 4. 什么是编译和反编译？ ★★★☆☆

- **编译（Compilation）**：指将高级语言（如Java源代码）转换成低级语言（如Java字节码）的过程。在Java中，这个过程由`javac`命令完成，它将`.java`源文件编译成`.class`字节码文件。
- **反编译（Decompilation）**：是编译的逆过程，指将字节码文件转换回可读的源代码。它常用于分析没有源码的第三方库，或者进行逆向工程。常用的反编译工具有JD-GUI、Fernflower等。

##### 5. Java是编译型还是解释型？Java是如何实现平台无关的？Java就是平台无关的吗？ ★★★★☆

- 编译型还是解释型？

  Java是一种**“半编译半解释型”或“混合型”**语言。

  1. **编译**：`.java`文件首先被`javac`**编译**成平台无关的`.class`字节码文件。
  2. **解释**：JVM启动时，**解释器**会逐行解释执行字节码。
  3. **JIT编译**：对于高频执行的“热点代码”，JVM的**即时编译器（JIT）**会将其再次编译成特定平台的本地机器码，以提高性能。

- 如何实现平台无关？

  关键在于JVM。Java代码被编译成一套统一的、与平台无关的字节码。不同的平台（Windows, macOS, Linux）有其各自专门的JVM实现。JVM就像一个“翻译官”，负责将这套通用的字节码翻译成对应平台的具体机器指令。

- Java就是平台无关的吗？

  基本上是，但不是绝对的。

  - **语言和字节码层面**：是平台无关的。
  - **JVM层面**：是**平台相关**的，每个平台都需要一个特定的JVM。
  - **代码层面**：如果代码中使用了与平台强相关的特性，如文件路径分隔符（Windows的`\` vs. Linux的`/`）、或者调用了本地库（JNI），那么这份代码就失去了平台无关性。

##### 6. 一个Java进程占用的内存有哪些部分？ ★★★☆☆

一个Java进程所占用的内存，主要指JVM的**运行时数据区（Runtime Data Areas）**，它分为两大类：

- **线程共享区域（Shared Among All Threads）**：
  1. **堆（Heap）**：最大的一块内存区域，用于存放**所有对象实例和数组**。是垃圾回收器（GC）管理的主要区域。
  2. **方法区（Method Area）**：用于存储已被虚拟机加载的**类信息、常量、静态变量、即时编译器编译后的代码**等数据。在JDK 8及以后，其实现被称为**元空间（Metaspace）**。
- **线程私有区域（Private to Each Thread）**：
  1. **程序计数器（Program Counter Register）**：一块较小的内存空间，记录当前线程正在执行的字节码指令的地址。
  2. **Java虚拟机栈（Java Virtual Machine Stack）**：每个方法在执行时都会创建一个**栈帧（Stack Frame）**，用于存储**局部变量表、操作数栈、动态链接、方法出口**等信息。
  3. **本地方法栈（Native Method Stack）**：与虚拟机栈类似，但它为虚拟机使用到的**本地（Native）方法**服务。

### 2. JVM 内存管理

#### 2.1 运行时数据区域

##### 1. JVM的运行时内存区域是怎样的？Java中的对象一定在堆上分配内存吗？ ★★★★☆

- **运行时内存区域**：JVM在执行Java程序时，会将其管理的内存划分为若干个不同的数据区域，主要包括：
  - **线程共享区域**：
    - **堆（Heap）**：存放对象实例和数组。
    - **方法区（Method Area）**：存储类信息、常量、静态变量等。
  - **线程私有区域**：
    - **Java虚拟机栈（VM Stack）**：存储方法调用的栈帧。
    - **本地方法栈（Native Method Stack）**：为Native方法服务。
    - **程序计数器（PC Register）**：记录当前线程执行的字节码行号。
- **对象不一定在堆上分配**：这个说法是正确的。通过现代JVM的编译器优化技术，对象分配有例外情况：
  1. **栈上分配（Stack Allocation）**：如果一个对象的作用域不会逃逸出方法外部（即只在方法内部使用），JIT编译器可能会进行**逃逸分析**，并将其直接在**栈上**分配。这样方法执行完毕后，对象随栈帧一同销毁，无需GC介入，极大地提升了性能。
  2. **标量替换（Scalar Replacement）**：如果一个对象可以被进一步分解为多个基本数据类型的成员变量，JIT编译器甚至可能不创建这个对象，而是将这些成员变量直接在栈上分配。

##### 2. Java运行时数据区域，导致内存溢出的原因有哪些？ ★★★★☆

不同区域的内存溢出（`OutOfMemoryError`, OOM）原因不同：

- **堆（Heap）溢出**：最常见。原因是创建了大量的对象，并且在垃圾回收后仍然无法获得足够空间。例如，内存泄漏（对象持有引用无法被GC）或数据量确实过大。
- **虚拟机栈和本地方法栈溢出**：通常表现为`StackOverflowError`。原因是**线程请求的栈深度**大于虚拟机所允许的深度，常见于无限递归或极深的函数调用。如果栈可以动态扩展，在无法申请到足够内存时也会抛出`OutOfMemoryError`。
- **方法区/元空间溢出**：原因是加载了过多的**类信息**。常见于运行时使用CGLIB等字节码技术动态生成大量类，或者加载了过多的第三方jar包。

##### 3. JVM的内存模型包括哪些部分？ ★★★☆☆

这个问题可能指代两个概念：

1. **运行时数据区（Runtime Data Areas）**：这是指JVM在内存中的结构划分，即上一题提到的堆、栈、方法区等。
2. **Java内存模型（JMM, Java Memory Model）**：这是一个更高层次的、关于并发编程的抽象规范，它定义了线程之间如何通过主内存进行通信，以及`volatile`、`synchronized`等关键字的内存可见性语义。

在面试中，通常需要根据上下文判断，但问“内存模型包括哪些部分”时，回答“运行时数据区”更常见。

##### 4. JVM堆和栈的区别是什么？JVM为什么要把堆和栈区分出来呢？ ★★★☆☆

| **特性**     | **堆（Heap）**             | **栈（Stack）**                        |
| ------------ | -------------------------- | -------------------------------------- |
| **共享性**   | **线程共享**               | **线程私有**                           |
| **存储内容** | 对象实例、数组             | 方法调用的栈帧（局部变量、操作数栈等） |
| **生命周期** | 与JVM生命周期基本一致      | 与线程生命周期一致，方法调用结束即销毁 |
| **空间大小** | 空间大，大小可调           | 空间小，大小通常固定                   |
| **管理方式** | 由垃圾回收器（GC）自动管理 | 由编译器自动分配和释放，无需GC         |

- 为什么要区分？

  这种区分是基于数据不同的生命周期和访问特性而做出的优化设计：

  1. **功能职责不同**：**栈**负责程序的**运行**，支持方法的调用和返回；**堆**负责数据的**存储**，容纳动态创建的对象。
  2. **管理效率不同**：栈的生命周期确定，管理简单高效。堆的管理复杂，需要通过GC来回收不再使用的对象。将两者分开，可以对它们采用不同的、最高效的管理策略。

##### 5. JVM方法区和堆区的区别是什么？ ★★★☆☆

- **存储内容不同**：
  - **堆区（Heap）**：主要存储**动态创建的对象实例**和**数组**。它的核心目的是存放“数据”本身。
  - **方法区（Method Area）**：主要存储**类的元数据**，如类结构信息、运行时常量池、静态变量、JIT编译后的代码等。它的核心目的是存放程序的“描述信息”和“静态数据”。
- **逻辑关系**：方法区在逻辑上是堆的一部分，但不同的JVM实现可以有不同的物理实现方式。

##### 6. 程序计数器的作用是什么？为什么它是唯一一个不会发生OutOfMemoryError的区域？ ★★★★☆

- **作用**：程序计数器是一块极小的内存空间，它可以看作是**当前线程所执行的字节码的行号指示器**。
  - 在多线程环境下，当线程被切换后，需要依靠程序计数器来恢复到正确的执行位置。
  - 它也是字节码解释器工作时，选取下一条要执行的字节码指令的依据。
- **为什么不会OOM**：因为每个线程的程序计数器在线程创建时就被分配了固定大小的内存空间，这个空间非常小，并且在其生命周期内大小不会改变。它只用于存储一个地址或偏移量，不涉及任何动态的数据增长，因此不存在内存耗尽的可能。

##### 7. Java虚拟机栈的作用是什么？它会发生哪些错误？ ★★★☆☆

- **作用**：Java虚拟机栈是**线程私有**的，它的生命周期与线程相同。它描述的是**Java方法执行的内存模型**：
  - 每个方法在执行时，都会创建一个对应的**栈帧（Stack Frame）**。
  - 栈帧用于存储**局部变量表、操作数栈、动态链接、方法出口**等信息。
  - 一个方法的调用过程，就对应一个栈帧在虚拟机栈中从入栈到出栈的过程。
- **会发生的错误**：
  1. **`StackOverflowError`**：如果线程请求的栈深度大于虚拟机所允许的深度（例如，无限递归），就会抛出此错误。
  2. **`OutOfMemoryError`**：如果虚拟机栈允许动态扩展，但在尝试扩展时无法申请到足够的内存，就会抛出此错误。

##### 8. Java堆的作用是什么？它会发生哪些错误？Java的堆是如何分代的？为什么要分代？ ★★★★★

- **作用**：Java堆是JVM所管理的内存中**最大的一块**，被所有线程共享。其唯一目的就是**存放对象实例**，几乎所有的对象实例和数组都在这里分配内存。
- **会发生的错误**：最常见的错误是 **`OutOfMemoryError: Java heap space`**。
- **堆的分代**：现代主流的垃圾回收器大都采用**分代收集算法**，将堆划分为：
  1. **新生代（Young Generation）**：存放新创建的对象。
     - **Eden区**：绝大多数对象在这里诞生。
     - **Survivor区（From / To）**：存放经过一次Minor GC后仍然存活的对象。
  2. **老年代（Old Generation / Tenured Generation）**：存放经过多次GC后仍然存活的对象，或者一些大对象。
- **为什么要分代**：这个设计的理论依据是“**弱分代假说**”——绝大多数对象都是“朝生夕死”的。
  - 通过分代，GC可以识别出哪些区域存放了大量“短命”对象，从而对这些区域使用**更高频、更低成本**的垃圾回收算法（如Minor GC）。
  - 而对于老年代中那些“长寿”对象，则使用**频率较低、但更彻底**的回收算法（如Major GC / Full GC）。
  - 这种“**分而治之**”的策略，极大地提升了垃圾回收的效率和性能。

##### 9. JVM中最大堆大小有没有限制？ ★★★☆☆

- **理论上**，最大堆大小受到物理内存和操作系统地址空间（32位/64位）的限制。
- **实践中**，最大堆大小由启动参数 **`-Xmx`** 来设定。如果不指定，JVM会根据物理内存大小计算一个默认值。

##### 10. 虚拟机中的堆一定是线程共享的吗？ ★★★☆☆

**逻辑上是，但实现上有优化**。

- 从**逻辑**上看，Java堆是所有线程共享的一块内存区域。
- 但为了**提升对象分配的效率**，避免多线程并发分配对象时因加锁带来的性能损耗，JVM为每个线程在Eden区中分配了一小块私有的内存区域，称为**本地线程分配缓冲（TLAB, Thread Local Allocation Buffer）**。
- 线程创建新对象时，会**优先在自己的TLAB中分配**。只有当TLAB用完或要分配大对象时，才需要加锁在共享的Eden区中分配。

##### 11. 什么是堆外内存？如何使用堆外内存？ ★★★☆☆

- **是什么**：堆外内存（Off-Heap Memory），也叫直接内存（Direct Memory），是指不受JVM堆内存管理的、直接由操作系统管理的内存。
- **如何使用**：主要通过`java.nio.ByteBuffer.allocateDirect(capacity)`方法来创建和使用。
- **优缺点**：
  - **优点**：在进行网络I/O或文件I/O时，可以**避免数据从Java堆拷贝到本地内存**的开销，从而提高性能。常用于NIO和一些高性能中间件（如Netty）。
  - **缺点**：分配和回收的成本较高，且不受JVM GC的直接管理，如果忘记手动释放，容易导致物理内存的泄漏。

##### 12. 方法区的作用是什么？JDK8前后方法区有什么变化？为什么JDK 1.8要废弃永久代，改用元空间？ ★★★★☆

- **作用**：方法区用于存储已被虚拟机加载的**类信息、常量、静态变量、即时编译器（JIT）编译后的代码缓存**等数据。

- **JDK 8前后变化**:

  - **JDK 1.7及以前**：方法区的实现被称为“**永久代（Permanent Generation）**”，它在物理上是**Java堆的一部分**，受GC管理。
  - **JDK 1.8及以后**：永久代被彻底移除，取而代之的是“**元空间（Metaspace）**”。元空间使用的是**本地内存（Native Memory）**，而不是虚拟机堆内存。

- **为什么废弃永久代**:

  1. **大小难以设定**：永久代大小在启动时固定，很难预估，容易导致`OutOfMemoryError`。
  2. **GC效率问题**：在永久代中进行GC的效率和效果不佳。
  3. **技术融合**：为了将HotSpot与JRockit（另一个没有永久代的JVM）的特性进行融合。

  - **元空间的优势**：元空间使用本地内存，其大小只受限于可用物理内存，大大降低了因方法区溢出导致OOM的风险。

##### 13. JVM方法区存储内容是否会动态扩展？是否会出现内存溢出？出现的原因有哪些？元空间满了（或溢出），可能是因为它吗？ ★★★★☆

- **是否动态扩展**：**是**。无论是永久代还是元空间，都可以通过参数设置初始大小和最大大小，并支持动态扩展。
- **是否会内存溢出**：**会**。当方法区无法满足新的内存分配请求时，会抛出`OutOfMemoryError`。
- **溢出的原因**:
  - 加载了过多的类（例如，Web应用在运行期间加载了大量的jar包）。
  - 运行时通过CGLIB、AspectJ等字节码技术动态生成了大量的代理类。
  - 字符串常量池中产生了大量的字符串（在JDK 7之前）。
- **元空间满了**：**是的**，在JDK 8及以后，方法区溢出的直接原因就是元空间（Metaspace）的内存耗尽。

##### 14. 什么是Class常量池、运行时常量池和字符串常量池？三者关系是什么？字符串常量池是如何实现的？ ★★★★☆

- **Class文件常量池（Class Constant Pool）**：
  - **存在位置**：存在于编译后的 **`.class` 文件**中。
  - **内容**：是**静态**的，存储了类的字面量（如字符串、final常量）和符号引用（如类和接口的全限定名、字段和方法的名称和描述符）。
- **运行时常量池（Runtime Constant Pool）**：
  - **存在位置**：在**方法区**中。
  - **内容**：是**动态**的。当类被加载时，其Class文件常量池中的内容会被存放到运行时常量池中。它还允许在运行时添加新的常量（如`String.intern()`）。
- **字符串常量池（String Constant Pool）**：
  - **存在位置**：在JDK 6及以前，位于永久代。从JDK 7开始，被移到了**Java堆**中。
  - **内容**：专门用于存储字符串字面量和通过`intern()`方法添加的字符串。
- **三者关系**：运行时常量池是Class文件常量池在内存中的体现。字符串常量池是运行时常量池的一个重要组成部分，但物理位置可能不同。
- **字符串常量池的实现**：在HotSpot中，它通常被实现为一个类似于`HashMap`的结构，存储着字符串常量的引用。

##### 15. 一个对象的结构是怎样的？ ★★★☆☆

在HotSpot虚拟机中，一个Java对象在内存中的布局可以分为三个部分：

1. **对象头（Header）**：
   - **Mark Word**：存储对象自身的运行时数据，如哈希码、GC分代年龄、锁状态标志、线程持有的锁等。
   - **类型指针（Class Pointer）**：指向该对象的类元数据（`Klass`对象）的指针，JVM通过它来确定这个对象是哪个类的实例。
   - **数组长度**（如果对象是数组）。
2. **实例数据（Instance Data）**：对象真正存储的有效信息，即程序代码中定义的各种字段内容。
3. **对齐填充（Padding）**：可选部分。为了保证对象的大小是8字节的整数倍，可能会有这部分填充字节，它不是必需的，仅仅起着占位符的作用。

##### 16. JVM是如何创建对象的？ ★★★☆☆

一个对象的创建过程大致如下：

1. **类加载检查**：当虚拟机遇到一条`new`指令时，首先检查这个指令的参数是否能在常量池中定位到一个类的符号引用，并检查这个类是否已被加载、解析和初始化。
2. **分配内存**：在堆中为新对象分配内存。分配方式有两种：
   - **指针碰撞（Pointer Bumping）**：如果堆内存是规整的，只需移动指针即可，速度快。
   - **空闲列表（Free List）**：如果堆内存不规整，需要维护一个列表来记录哪些内存块是可用的。
3. **初始化零值**：内存分配完成后，虚拟机将分配到的内存空间（不包括对象头）都初始化为零值（如`0`, `null`, `false`）。
4. **设置对象头**：虚拟机对对象进行必要的设置，例如这个对象是哪个类的实例、如何才能找到类的元数据信息、对象的哈希码、对象的GC分代年龄等信息。
5. **执行`<init>`方法**：执行对象的构造函数，按照开发者的意图对对象进行初始化。

#### 2.2 内存管理细节

##### 1. JVM如何管理堆内存？ ★★★☆☆

JVM通过**垃圾回收器（Garbage Collector, GC）**来自动管理堆内存。核心工作包括：

1. **对象分配**：为新对象分配内存空间（通过指针碰撞或空闲列表，以及TLAB优化）。
2. **垃圾识别**：通过**可达性分析算法（Reachability Analysis）**，从GC Roots开始遍历，找出所有存活的对象。
3. **垃圾回收**：对不再存活的对象所占用的内存进行回收。主要使用**标记-清除**、**标记-复制**、**标记-整理**等算法。
4. **分代管理**：将堆分为新生代和老年代，使用不同的GC策略来提高回收效率。

##### 2. JVM如何管理栈内存？ ★★★☆☆

栈内存的管理是**自动且高效**的。

1. **栈帧**：以**栈帧**为单位进行管理。
2. **生命周期**：每次方法调用，都会创建一个栈帧并**入栈**；方法执行完毕，对应的栈帧就**出栈**并被销毁。
3. **自动管理**：整个过程由编译器和JVM自动完成，无需开发者干预，也不需要垃圾回收器介入。

##### 3. JVM如何管理方法区？ ★★★☆☆

方法区的管理也涉及到垃圾回收，但回收内容和条件更苛刻。其GC主要回收两部分内容：

1. **废弃的常量**：如果一个常量（如字符串）不再被任何地方引用，就可以被回收。
2. **不再使用的类**：要卸载一个类，条件非常苛刻，必须同时满足：
   - 该类的所有实例都已被回收。
   - 加载该类的`ClassLoader`已被回收。
   - 该类的`java.lang.Class`对象没有任何地方被引用。

##### 4. JVM如何管理本地方法栈？ ★★★☆☆

本地方法栈与Java虚拟机栈非常相似，区别在于它为**本地（Native）方法**服务。其管理方式也类似于虚拟机栈，当调用本地方法时创建栈帧，调用结束后销毁。具体的管理由JVM的具体实现和底层操作系统来决定。

### 3. JVM 垃圾回收

#### 3.1 垃圾回收基础

##### 1. 什么是垃圾回收？ ★★★☆☆

垃圾回收（Garbage Collection, GC）是一种**自动化的内存管理机制**。它负责在程序运行时，自动地**识别并回收**那些不再被程序使用的对象（即“垃圾”）所占用的内存，从而避免内存泄漏和内存溢出。

##### 2. JVM是如何判断对象是否存活的？ ★★★☆☆

主要有两种算法，但现代JVM都使用第二种：

1. **引用计数法（Reference Counting）**：为每个对象维护一个引用计数器。当有引用指向它时，计数器加1；引用失效时，减1。当计数器为0时，对象即为垃圾。
   - **缺点**：无法解决**循环引用**问题。
2. **可达性分析算法（Reachability Analysis）**：这是当前主流的算法。它从一系列称为“**GC Roots**”的根对象开始，向下遍历对象引用图。所有从GC Roots能够到达的对象都被标记为**存活对象**，而所有不可达的对象则被视为垃圾。

##### 3. 什么是可达性分析算法？GC Roots有哪些？ ★★★★☆

- **可达性分析算法**：其基本思路是通过一系列的“GC Roots”对象作为起始点，从这些节点开始向下搜索，搜索所走过的路径称为引用链（Reference Chain）。当一个对象到GC Roots没有任何引用链相连时，则证明此对象是不可用的。
- **常见的GC Roots包括**：
  1. **虚拟机栈（栈帧中的本地变量表）中引用的对象**。
  2. **方法区中类静态属性引用的对象**。
  3. **方法区中常量引用的对象**。
  4. **本地方法栈中JNI（即一般说的Native方法）引用的对象**。
  5. 被同步锁（`synchronized`）持有的对象。

##### 4. 什么是三色标记算法？ ★★★★☆

三色标记（Tri-color Marking）是**可达性分析算法**在**并发标记**阶段的一种实现方式。它将所有对象逻辑上分为三种颜色：

- **白色**：表示对象**尚未被**垃圾回收器访问过。在标记阶段结束后，仍为白色的对象即为垃圾。
- **灰色**：表示对象**已被**垃圾回收器访问过，但这个对象至少还有一个引用没有被扫描过。
- **黑色**：表示对象**已被**垃圾回收器访问过，且这个对象的所有引用也都已经被扫描过了。

**并发标记的问题**：在标记过程中，如果应用程序的线程修改了对象引用关系，可能会导致“**对象消失**”（漏标）的问题。现代并发GC（如CMS, G1）通过**写屏障（Write Barrier）**和一些辅助数据结构（如`Remembered Set`）来解决这个问题。

##### 5. 什么是强引用、软引用、弱引用和虚引用？ ★★★★☆

这是Java提供的四种不同强度的引用类型：

- **强引用（Strong Reference）**：最常见的引用，如`Object obj = new Object()`。只要强引用存在，垃圾回收器**永远不会**回收被引用的对象。
- **软引用（Soft Reference）**：用来描述一些还有用但非必需的对象。只有在**内存不足**将要发生内存溢出时，才会回收这些对象。适合用来实现**内存敏感的高速缓存**。
- **弱引用（Weak Reference）**：强度比软引用更弱。被弱引用关联的对象只能生存到**下一次垃圾收集**发生为止。一旦发生GC，无论当前内存是否充足，都会回收只被弱引用关联的对象。`WeakHashMap`就是利用了这个特性。
- **虚引用（Phantom Reference）**：也叫“幽灵引用”，是最弱的一种引用关系。它完全不影响对象的生命周期。其唯一目的就是希望能在这个对象被回收时收到一个系统通知，以便进行一些后续清理工作，必须和**引用队列（`ReferenceQueue`）**联合使用。

##### 6. 什么是垃圾回收的“Stop-the-world”（STW）事件？STW有什么影响？ ★★★★★

- **是什么**：Stop-the-World（STW）是指在执行垃圾回收时，JVM会**暂停所有正在运行的应用程序线程**，直到GC过程完全结束。
- **影响**：STW会导致应用程序的**停顿**，在停顿期间，所有服务都将暂停，无法响应用户请求。STW的时间长短是衡量一个垃圾回收器性能好坏的重要指标。现代GC（如G1, ZGC）的主要目标就是**尽可能地缩短STW的时间**。

##### 7. 为什么初始标记和重新标记需要STW，而并发标记不需要？ ★★★★★

这是针对CMS、G1等并发垃圾回收器而言的：

- **初始标记（Initial Mark）**：这个阶段只标记**GC Roots能直接关联到**的对象。这个过程非常快，为了保证标记的准确性（不漏掉任何一个根），需要一个短暂的STW。
- **并发标记（Concurrent Mark）**：这个阶段会从初始标记的对象开始，遍历整个对象图。这个过程非常耗时，因此它被设计为可以和应用程序线程**并发执行**，从而避免了长时间的STW。
- **重新标记（Remark）**：在并发标记期间，应用程序线程可能**修改了对象的引用关系**，导致之前的标记结果失效（比如漏标）。重新标记阶段就是为了**修正**这些在并发标记期间产生的变动。这个过程也需要一个短暂的STW来保证数据的一致性。

##### 8. YoungGC和FullGC的触发条件是什么？ ★★★★☆

- **Young GC（或 Minor GC）**：
  - 主要触发条件：当新生代的**Eden区被占满**时触发。
- **Full GC（或 Major GC）**：
  - 主要触发条件：
    1. **老年代空间不足**：当老年代的连续空间小于新生代历次晋升对象的平均大小时。
    2. **方法区/元空间不足**。
    3. **显示调用`System.gc()`**（但不保证立即执行）。
    4. **新生代晋升失败（Promotion Failure）**：在进行Young GC时，存活对象的大小超过了Survivor区或老年代的可用空间。

##### 9. FullGC多久一次算正常？ ★★★★☆

**没有固定的标准**。一个健康的系统应该**尽可能地少发生甚至不发生Full GC**。

- 频繁的Full GC（例如几分钟或几小时一次）通常是**性能问题的信号**，可能意味着存在内存泄漏、或者堆内存分配不合理（如新生代太小导致对象过早晋升）。
- 理想情况下，应该通过合理的内存配置和代码优化，让绝大多数对象在Young GC中就被回收，避免对老年代造成压力。

##### 10. Java发生OOM一定会导致JVM退出吗？ ★★★☆☆

**不一定**。

- 当一个线程因为无法分配内存而抛出`OutOfMemoryError`时，这个**线程通常会终止**。
- 但是，如果这个异常被捕获了，或者其他**非守护线程**仍然在正常运行，那么**JVM进程不会退出**。

##### 11. 哪些语言有GC机制？ ★★★☆☆

除了Java，还有很多现代编程语言都内置了GC机制，例如：

- **C#**

- **Python**

- **Go**

- **JavaScript**

- **Ruby**

- Scala, Kotlin (基于JVM)

  而像C和**C++**则依赖于手动的内存管理。

#### 3.2 垃圾回收算法与分代

##### 1. JVM垃圾回收的基本算法有哪些？它们各自的原理和特点是什么？ ★★★★★

主要有三种基础算法：

1. **标记-清除（Mark-Sweep）**：
   - **原理**：分为“标记”和“清除”两个阶段。首先标记出所有需要回收的对象，标记完成后统一回收所有被标记的对象。
   - **特点**：实现简单，但会产生大量**内存碎片**，导致后续无法为大对象分配连续内存。
2. **标记-复制（Mark-Copy）**：
   - **原理**：将可用内存按容量划分为大小相等的两块。每次只使用其中一块。当这一块的内存用完了，就将还存活着的对象复制到另外一块上面，然后再把已使用过的内存空间一次清理掉。
   - **特点**：实现简单，运行高效，**没有内存碎片**。但代价是**浪费了一半的内存空间**。
3. **标记-整理（Mark-Compact）**：
   - **原理**：标记过程与“标记-清除”一样，但后续步骤不是直接对可回收对象进行清理，而是让所有存活的对象都向内存空间一端移动，然后直接清理掉边界以外的内存。
   - **特点**：**解决了内存碎片问题**，但因为涉及对象的移动，效率比“标记-清除”要低。

##### 5. 什么是分代垃圾回收？新生代和老年代的GC算法？新生代和老年代的垃圾收集策略有什么不同？ ★★★★☆

- **什么是分代**：基于“绝大多数对象都是朝生夕死”的**弱分代假说**，将Java堆划分为**新生代（Young Generation）\**和\**老年代（Old Generation）**，以便根据不同年代的特点采用最适当的收集算法。
- **GC算法**:
  - **新生代**：对象存活率低，适合使用**标记-复制**算法。新生代内部又分为一个Eden区和两个Survivor区（From/To），它们之间的比例通常是8:1:1。
  - **老年代**：对象存活率高，适合使用**标记-清除**或**标记-整理**算法。
- **收集策略不同**：
  - **新生代GC（Minor GC）**：回收**频率高**，**速度快**，STW时间短。
  - **老年代GC（Major GC/Full GC）**：回收**频率低**，**速度慢**，STW时间长。

##### 6. 新生代如果只有一个Eden和一个Survivor可以吗？ ★★★★☆

**不可以**。

- **原因**：新生代采用的是**标记-复制算法**。这个算法需要一个**目标空间**来存放存活的对象。
- 如果只有一个Survivor区，那么当Eden区满进行GC时，存活的对象需要被复制。它们往哪里复制呢？如果直接复制到这唯一的Survivor区，那么这个Survivor区中原有的（上一次GC后存活的）对象怎么办？如果直接复制到老年代，那Survivor区就失去了其作为“缓冲地带”和“对象年龄筛选器”的作用，会导致大量短命对象过早进入老年代，引发频繁的Full GC。
- 因此，必须要有**两个Survivor区**（通常称为From和To），一个用作本次GC后存活对象的目的地，另一个则保持空闲，两者角色在每次GC后交换。

##### 7. 什么是跨代引用，有什么问题？ ★★★★☆

- **是什么**：指一个**老年代对象**引用了一个**新生代对象**。
- **有什么问题**：在进行**Minor GC**时，为了判断新生代的对象是否存活，我们需要知道是否有老年代的对象在引用它。如果不知道，就必须**扫描整个老年代**来查找跨代引用，这会让Minor GC的成本变得极高，失去了分代的意义。
- **解决方案**：**记忆集（Remembered Set）\**和\**卡表（Card Table）**。JVM在老年代中维护一个叫做“卡表”的数据结构，它将老年代划分为一个个小块（“卡页”）。当一个老年代对象发生写操作，且其引用指向了新生代对象时，JVM就会在这个老年代对象所在的卡页上做一个“标记”（将其置“脏”）。这样，在Minor GC时，只需扫描那些被标记为“脏”的卡页，而无需扫描整个老年代。

##### 8. 说一说JVM的并发回收和并行回收。 ★★★★☆

- **并行（Parallel）**：指**多条垃圾收集器线程并行工作**，但此时**用户线程仍然处于等待状态（STW）**。它关注的是缩短GC的**总停顿时间**，提高**吞吐量**。
- **并发（Concurrent）**：指垃圾收集器线程与**用户线程同时执行**（不一定是并行的，可能会交替执行）。它关注的是**尽可能缩短单次停顿时间**，以获得更好的用户体验。

##### 9. JVM一次完整的GC流程是怎样的？ ★★★★☆

1. **对象诞生**：绝大多数新对象在**Eden区**分配。
2. **Eden区满，触发Minor GC**：
   - 对Eden区进行可达性分析，找出存活对象。
   - 将存活对象复制到**空的Survivor区（To区）**，并将其年龄加1。
   - 对正在使用的Survivor区（From区）也进行可达性分析，将其中的存活对象也复制到To区，并将其年龄加1。
   - 清空Eden区和From区。
   - 交换From区和To区的角色。
3. **反复Minor GC**：上述过程重复多次，对象在两个Survivor区之间来回复制，其年龄不断增加。
4. **对象晋升（Promotion）**：当一个对象的年龄达到某个阈值（默认为15）后，它会被**晋升**到**老年代**。另外，如果Survivor空间不足以容纳所有存活对象，也会直接晋升。
5. **老年代满，触发Major GC/Full GC**：对整个堆（包括新生代和老年代）进行一次彻底的垃圾回收，STW时间较长。

#### 3.3 垃圾回收器

##### 1. JVM的垃圾回收器有哪些？它们各自的特点和适用场景是什么？如何选择垃圾回收器？ ★★★★★

- **有哪些**：
  1. **Serial / Serial Old**: 单线程收集器，简单高效，但会STW。适用于客户端模式或单核服务器。
  2. **ParNew**: Serial的多线程版本，用于新生代。
  3. **Parallel Scavenge / Parallel Old**: **吞吐量优先**的收集器，关注在单位时间内完成更多任务。JDK 8的默认选择。适用于后台计算、数据处理等对停顿不敏感的场景。
  4. **CMS (Concurrent Mark Sweep)**: **低停顿**的收集器，以并发方式进行大部分GC工作。适用于对响应时间有高要求的互联网应用。
  5. **G1 (Garbage-First)**: **可预测停顿时间**的收集器，将堆划分为多个Region，兼顾吞吐量和低停顿。JDK 9及以后的默认选择。
  6. **ZGC / Shenandoah**: 面向未来的**极低停顿**（亚毫秒级）收集器，适用于超大堆内存和对延迟极度敏感的应用。
- **如何选择**：
  - **响应时间优先**：选择 **G1** 或 **ZGC**。
  - **吞吐量优先**：选择 **Parallel Scavenge**。
  - **没有特殊要求**：使用**对应JDK版本的默认收集器**即可（JDK 8用Parallel，JDK 9+用G1）。

##### 2. CMS（Concurrent Mark-Sweep）垃圾回收器的原理是什么？介绍CMS的垃圾回收过程。 ★★★★★

- **原理**：CMS是一款以获取**最短回收停顿时间**为目标的收集器。它基于**标记-清除**算法，并允许垃圾收集线程与用户线程在大部分时间内并发执行。
- **回收过程**：
  1. **初始标记（Initial Mark）**：**STW**。标记GC Roots能直接关联到的对象，速度很快。
  2. **并发标记（Concurrent Mark）**：与用户线程**并发执行**。从初始标记的对象开始，遍历整个对象图。
  3. **重新标记（Remark）**：**STW**。修正并发标记期间因用户程序继续运作而导致标记产生变动的那一部分对象的标记记录。
  4. **并发清除（Concurrent Sweep）**：与用户线程**并发执行**。清除未被标记的垃圾对象。

##### 3. G1垃圾回收器如何与CMS进行对比？为什么G1从JDK 9之后成为默认的垃圾回收器？ ★★★★★

| **特性**     | **CMS**                     | **G1**                                                 |
| ------------ | --------------------------- | ------------------------------------------------------ |
| **内存布局** | 传统的**新生代/老年代**划分 | 将堆划分为多个大小相等的**Region**                     |
| **回收算法** | **标记-清除**               | 整体上是**标记-整理**，局部（Region间）是**标记-复制** |
| **内存碎片** | **会产生**                  | **不会产生**                                           |
| **停顿时间** | **不可预测**                | **可预测**（通过`-XX:MaxGCPauseMillis`设定）           |
| **回收范围** | 主要针对老年代              | 可同时回收新生代和老年代（Mixed GC）                   |

- **为什么G1成为默认**：G1是更先进、更全能的垃圾回收器。它通过引入Region和可预测停顿模型，很好地**平衡了吞吐量和低停顿**的需求，同时从根本上**解决了CMS的内存碎片问题**，使得其在各种应用场景下都表现得更加稳定和可靠。

##### 4. JDK 11中新出的ZGC有什么特点？JDK 8和Java 11的GC有什么区别？ ★★★★☆

- **ZGC的特点**：
  - **极低的停顿时间**：STW时间不随堆大小或存活对象数量的增加而增加，通常在**1毫秒以内**。
  - **支持超大堆内存**：能够轻松管理TB级别的堆内存。
  - **原理**：基于**着色指针（Colored Pointers）**和**读屏障（Load Barrier）**技术，使得几乎所有的GC工作（标记、转移、重定位）都可以并发执行。
- **JDK 8和JDK 11的GC区别**：
  - **默认GC**: JDK 8默认是**Parallel Scavenge + Parallel Old**。JDK 11默认是**G1**。
  - **新GC引入**: JDK 11引入了实验性的**ZGC**和**Epsilon GC**（一个什么都不做的GC，用于性能分析）。

##### 5. 新生代和老年代的垃圾回收器有何区别？ ★★★★☆

（此题答案与3.2.5核心内容重合，可参考对应问题回答。关键在于新生代GC快、频、用复制算法；老年代GC慢、少、用标记-清除/整理算法。）

##### 6. G1和CMS有什么区别？ ★★★★☆

（此题答案与3.3.3核心内容重合，可参考对应问题回答。）

##### 7. 项目中如何选择垃圾回收器？为啥选择这个？ ★★★★☆

选择垃圾回收器是一个权衡的过程，主要考虑以下因素：

1. **JDK版本**：默认选择该JDK版本推荐的GC（JDK 8用Parallel，9+用G1）。
2. **业务场景**：
   - **后台计算/大数据处理**：对吞吐量要求高，对停顿不敏感，可选**Parallel Scavenge**。
   - **Web应用/API服务**：对响应时间要求高，希望停顿短，可选**G1**或**CMS**（在老版本JDK上）。
3. **堆内存大小**：
   - 如果堆内存非常大（几十G甚至上百G），且对延迟要求极高，可以考虑使用**ZGC**。
4. **压测调优**：最终的选择应该基于**实际的压力测试**结果，通过分析GC日志来调整参数，找到最适合自己应用的GC组合和配置。

#### 3.4 垃圾对象生命周期

##### 1. 对象的finalize()方法什么时候被调用？它用来做什么？ ★★★☆☆

- **调用时机**：当一个对象在可达性分析后被判断为**不可达**时，如果该对象重写了`finalize()`方法且尚未被调用过，GC并不会立即回收它，而是会将其放入一个叫做“F-Queue”的队列中。稍后，一个由JVM自动建立的、低优先级的Finalizer线程会去执行这个队列中对象的`finalize()`方法。
- **作用**：`finalize()`方法是对象在被回收前，进行**最后一次“自救”**的机会。开发者可以在这个方法中编写一些资源释放的代码。

##### 2. 为什么不推荐使用finalize()方法进行资源清理？ ★★★★☆

因为`finalize()`存在诸多严重问题：

1. **执行时机不确定**：JVM不保证`finalize()`方法何时执行，甚至不保证它一定会被执行。
2. **性能问题**：它会严重影响GC的性能，因为涉及到对象的两次标记和额外的线程调度。
3. **可能导致对象复活**：如果在`finalize()`方法中，将`this`重新赋值给一个GC Roots可达的引用，这个本该被回收的对象就会“复活”，扰乱了GC的正常工作。
4. **容易引发错误**：`finalize()`方法在执行过程中如果抛出异常，会被忽略，且不会影响其他对象的终结过程。

- **替代方案**：使用`try-with-resources`语句或在`finally`块中显式地调用`close()`方法来释放资源，这是更安全、更可靠的方式。

### 4. 类加载机制

#### 4.1 类加载基础

##### 1. JVM的类加载机制是什么？ ★★★★★

JVM的类加载机制是指虚拟机把描述类的数据从**`.class`文件**加载到内存，并对数据进行**校验、转换解析和初始化**，最终形成可以被虚拟机直接使用的Java类型的过程。

##### 2. 类从被加载到虚拟机内存中到卸载出内存，会经历哪些阶段？ ★★★★☆

一个类的完整生命周期包括以下7个阶段：

1. **加载（Loading）**
2. **验证（Verification）**
3. **准备（Preparation）**
4. **解析（Resolution）**
5. **初始化（Initialization）**
6. **使用（Using）**
7. **卸载（Unloading）**

其中，验证、准备、解析三个部分统称为**链接（Linking）**。

##### 3. 类加载的每个阶段具体做什么？ ★★★★☆

1. **加载（Loading）**：
   - 通过一个类的全限定名来获取定义此类的二进制字节流。
   - 将这个字节流所代表的静态存储结构转化为方法区的运行时数据结构。
   - 在内存中生成一个代表这个类的`java.lang.Class`对象，作为方法区这个类的各种数据的访问入口。
2. **验证（Verification）**：确保`.class`文件的字节流中包含的信息符合当前虚拟机的要求，并且不会危害虚拟机自身的安全。
3. **准备（Preparation）**：为**类变量（静态变量）\**分配内存并设置其\**初始零值**。例如`public static int value = 123;`在准备阶段`value`的值是`0`而不是`123`。
4. **解析（Resolution）**：将常量池内的**符号引用**替换为**直接引用**的过程。
5. **初始化（Initialization）**：真正开始执行类中定义的Java程序代码。这个阶段是执行**类构造器`<clinit>()`方法**的过程，为静态变量赋予正确的初始值。

##### 4. Java中的类什么时候会被加载？ ★★★★☆

JVM规范没有强制规定类必须在何时被加载，但严格规定了有且只有6种情况必须立即对类进行“**初始化**”（而加载、验证、准备自然需要在此之前完成），这被称为**主动引用**：

1. 遇到`new`、`getstatic`、`putstatic`或`invokestatic`这4条字节码指令时。
2. 使用`java.lang.reflect`包的方法对类型进行反射调用的时候。
3. 当初始化类的时候，如果发现其父类还没有进行过初始化，则需要先触发其父类的初始化。
4. 当虚拟机启动时，用户需要指定一个要执行的主类（包含`main()`方法的那个类），虚拟机会先初始化这个主类。
5. 当使用JDK 7新加入的动态语言支持时。
6. 当一个接口定义了JDK 8新加入的默认方法时，如果这个接口的实现类发生了初始化，那该接口要在其之前被初始化。

##### 5. 如何确定被加载类在Java虚拟机的唯一性？如何判断JVM中类和其他类是不是同一个类？ ★★★★☆

在JVM中，判断两个类是否“相等”，必须同时满足两个条件：

1. 由**同一个类加载器（ClassLoader）**加载。
2. 类的**全限定名（Fully Qualified Class Name）**必须相同。

即使两个类的`.class`文件来源于同一个物理文件，只要加载它们的类加载器不同，那么这两个类在JVM中就是两个不同的、独立的类型。

##### 6. 类的生命周期是怎样的？ ★★★★☆

（此题答案与第2题“类从被加载到虚拟机内存中到卸载出内存，会经历哪些阶段？”核心内容重合，请参考该题答案。）

类的生命周期就是指其加载、链接（验证、准备、解析）、初始化、使用和卸载这七个阶段。

##### 7. Java中类加载的过程是怎样的？ ★★★★☆

（此题答案与第3题“类加载的每个阶段具体做什么？”核心内容重合，请参考该题答案。）

类加载的过程主要包括加载、验证、准备、解析和初始化这五个阶段。

#### 4.2 类加载器与双亲委派

##### 1. 什么是双亲委派模型？它的工作流程是怎样的？有什么优势？如何破坏？破坏双亲委派之后，能重写String类吗？ ★★★★★

- **是什么**：双亲委派模型（Parents Delegation Model）是Java类加载器的一种工作机制。它要求除了顶层的启动类加载器外，其余的类加载器都应当有自己的父类加载器。
- **工作流程**：
  1. 当一个类加载器收到类加载请求时，它首先**不会自己去尝试加载**这个类。
  2. 而是把这个请求**委派给父类加载器**去完成。
  3. 每一层次的类加载器都是如此，因此所有的加载请求最终都应该传送到最顶层的**启动类加载器**中。
  4. 只有当**父加载器反馈自己无法完成**这个加载请求（它的搜索范围中没有找到所需的类）时，**子加载器才会尝试自己去加载**。
- **优势**：
  1. **避免类的重复加载**：保证了Java类的唯一性。因为无论哪个加载器加载，最终都会委派给顶层的加载器，确保了同一个类只会被加载一次。
  2. **保证安全性**：防止核心API库被随意篡改。例如，通过双亲委派，用户自定义的`java.lang.String`类永远不会被加载，因为启动类加载器会优先加载JDK自带的`String`类。
- **如何破坏**：通过重写`ClassLoader`的`loadClass()`方法，在方法中不遵循先委派给父加载器的逻辑，而是先尝试自己加载。Tomcat的WebAppClassLoader就是典型的破坏双亲委派模型的例子，用于实现Web应用间的类隔离。
- **能重写String类吗？**：**不能**。即使破坏了双亲委派模型，也无法重写`java.lang.String`。因为JVM在加载`java.lang`包下的核心类时，会进行额外的安全检查，禁止用户使用自定义的类加载器来加载这些核心类。

##### 2. 类加载器有哪些类型？它们分别负责加载哪种类型的类？ ★★★★☆

主要有三类：

1. **启动类加载器（Bootstrap ClassLoader）**：由C++实现，是虚拟机自身的一部分。负责加载`<JAVA_HOME>\lib`目录下的，或者被`-Xbootclasspath`参数所指定的路径中存放的核心类库（如`rt.jar`）。
2. **扩展类加载器（Extension ClassLoader）**：负责加载`<JAVA_HOME>\lib\ext`目录下的，或者被`java.ext.dirs`系统变量所指定的路径中所有的类库。
3. **应用程序类加载器（Application ClassLoader）**：也叫系统类加载器。它负责加载用户类路径（Classpath）上所指定的类库。开发者编写的Java类通常都是由它来加载的。

##### 3. 如何自定义一个类加载器？ ★★★☆☆

通常通过**继承`java.lang.ClassLoader`类**，并重写其**`findClass()`方法**来实现。

```
public class MyClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        // 1. 根据类的全限定名，获取类的二进制字节流（例如从文件、网络读取）
        byte[] b = loadClassData(name);
        // 2. 调用defineClass()方法将字节数组转换为Class对象
        return defineClass(name, b, 0, b.length);
    }
    // ... loadClassData方法的具体实现
}
```

##### 4. 两个war依赖相同的jar包，部署在同一个tomcat，类会重复加载吗？ ★★★★☆

**会重复加载**。

- Tomcat的每个Web应用（war包）都有一个自己专属的类加载器（WebAppClassLoader）。
- 为了实现Web应用之间的类隔离（例如，应用A使用Spring 4，应用B使用Spring 5），Tomcat破坏了双亲委派模型。
- 当加载Web应用自身的类（如`WEB-INF/lib`下的jar包）时，WebAppClassLoader会优先自己加载，而不是先委派给父加载器。
- 因此，即使两个war包依赖了同一个版本的jar包，它们也会被各自的WebAppClassLoader分别加载一次，在JVM中形成两个独立的`Class`对象。

##### 5. JDK1.8和1.9中类加载器有哪些不同？ ★★★☆☆

最大的变化是JDK 9引入了**模块化系统（JPMS）**。

- **扩展类加载器被取代**：在JDK 9中，扩展类加载器被**平台类加载器（Platform ClassLoader）**所取代。
- **加载范围改变**：启动类加载器、平台类加载器和应用程序类加载器都继承自`BuiltinClassLoader`，它们的加载范围由模块定义来决定，而不再是简单的目录路径。双亲委派模型本身仍然存在，但其委派关系和类搜索的方式发生了改变。

### 5. JVM 性能调优

#### 5.1 调优目标与方法

##### 1. 为什么要进行JVM调优？ ★★★☆☆

主要目的是为了**提升应用程序的性能**和**保障其稳定性**。

- **性能方面**：减少GC的频率和停顿时间（STW），提高应用的响应速度和吞吐量。
- **稳定性方面**：避免因内存溢出（OOM）、栈溢出等问题导致应用崩溃。

##### 2. JVM调优的总体流程是什么？ ★★★★☆

1. **明确调优目标**：确定性能指标（如响应时间、吞吐量、GC频率等）。
2. **发现性能瓶颈**：通过监控工具（如JMX、VisualVM、Arthas）收集运行时数据，定位问题。
3. **性能分析**：分析GC日志、堆转储快照（Heap Dump）、线程快照（Thread Dump），找出瓶颈根源。
4. **提出调优方案**：根据分析结果，调整JVM参数、优化代码逻辑或调整系统架构。
5. **验证调优结果**：进行压力测试，对比调优前后的性能指标，验证方案有效性。
6. **持续监控**：上线后持续监控，确保系统稳定运行。

##### 3. JVM性能调优的基本方法有哪些？ ★★★★★

1. **设置合适的堆大小**：通过`-Xms`（初始堆大小）和`-Xmx`（最大堆大小）参数，避免堆的频繁伸缩。
2. **选择合适的垃圾回收器**：根据应用场景（吞吐量优先还是响应时间优先）选择合适的GC，如Parallel Scavenge、G1、ZGC。
3. **调整分代大小**：通过`-Xmn`或`-XX:NewRatio`等参数调整新生代与老年代的比例，让对象尽可能在新生代被回收。
4. **代码层面优化**：
   - 减少大对象的创建。
   - 避免内存泄漏，及时释放不再使用的对象引用。
   - 使用线程池等技术合理管理线程。

##### 4. JVM性能调优的原则有哪些？ ★★★☆☆

1. **基于数据**：调优必须基于监控和分析数据，而不是凭感觉猜测。
2. **由点到面**：优先解决最主要的性能瓶颈。
3. **循序渐进**：一次只调整一个参数或一小部分代码，便于评估效果。
4. **适可而止**：JVM调优有边际效应，过度调优可能效果不佳甚至适得其反。

##### 5. JVM性能调优的依据是什么？ ★★★☆☆

主要依据是**JVM的运行时数据**，包括：

- **GC日志**：包含了每次GC的类型、原因、耗时、回收前后内存变化等详细信息，是分析GC性能问题的最重要依据。
- **堆转储快照（Heap Dump）**：分析内存泄漏和对象分布的利器。
- **线程快照（Thread Dump）**：分析死锁、线程等待、CPU占用率过高等问题的关键。
- **实时监控数据（JMX）**：通过监控工具实时观察堆内存、线程数、GC次数等指标的变化。

##### 6. JVM性能调优的指标有哪些？ ★★★☆☆

1. **吞吐量（Throughput）**：用户代码运行时间 / (用户代码运行时间 + GC时间)。
2. **停顿时间（Pause Time）**：因GC而导致应用暂停（STW）的时间。
3. **GC频率（GC Frequency）**：单位时间内GC发生的次数。
4. **内存占用（Footprint）**：应用稳定运行时占用的堆内存大小。

#### 5.2 调优工具与实践

##### 1. 如何调整JVM堆内存大小？ ★★★☆☆

通过设置JVM启动参数：

- **`-Xms<size>`**：设置初始堆大小。
- **`-Xmx<size>`**：设置最大堆大小。
- **最佳实践**：通常建议将`-Xms`和`-Xmx`**设置为相同的值**，以避免在运行时因堆的自动伸缩而带来的性能开销。

##### 4. JDK自带的JVM监控和故障处理工具有哪些？ ★★★★☆

##### 5. 如何使用jstack、jmap、jstat等工具进行JVM故障排查？ ★★★★★

1. **定位进程ID**：使用`jps -l`找到需要排查的Java进程ID。
2. **CPU占用过高**:
   - 使用`top -H -p <pid>`找出占用CPU最高的线程ID（tid）。
   - 将线程ID转换为16进制 (`printf "%x\n" <tid>`)。
   - 使用`jstack <pid> | grep <hex_tid> -A 30`查看该线程的堆栈，定位问题代码。
3. **内存泄漏/OOM**:
   - 使用`jmap -heap <pid>`查看堆的整体使用情况。
   - 使用`jmap -dump:format=b,file=heap.hprof <pid>`生成堆转储快照。
   - 使用MAT (Memory Analyzer Tool) 等工具分析`.hprof`文件，找出内存泄漏的根源。
4. **GC频繁/性能问题**:
   - 使用`jstat -gcutil <pid> 1000`每秒打印一次GC统计信息，观察各分代内存和GC次数的变化。
   - 分析GC日志，定位是Minor GC频繁还是Full GC频繁，以及原因。
5. **死锁/线程等待**:
   - 使用`jstack <pid>`生成线程快照，`jstack`会自动检测并报告死锁。
   - 分析线程状态（`BLOCKED`, `WAITING`），查看线程在等待哪个锁或资源。

##### 6. JVM性能调优的常用参数有哪些？ ★★★☆☆

- **堆设置**: `-Xms`, `-Xmx`, `-Xmn`, `-XX:NewRatio`
- **GC器选择**: `-XX:+UseSerialGC`, `-XX:+UseParallelGC`, `-XX:+UseConcMarkSweepGC`, `-XX:+UseG1GC`, `-XX:+UseZGC`
- **GC日志**: `-Xlog:gc*...` (JDK 9+)
- **OOM快照**: `-XX:+HeapDumpOnOutOfMemoryError`, `-XX:HeapDumpPath=<path>`

##### 7. 什么是safe point？有啥用？ ★★★☆☆

- **是什么**：安全点（Safe Point）是代码中的一些特定位置，在这些位置上，线程的状态是确定的，并且JVM可以安全地进行一些需要暂停所有线程的操作（如GC）。
- **有啥用**：当需要进行Stop-The-World时（如GC、类重定义等），JVM不会立即暂停所有线程，而是等待所有线程都运行到最近的一个安全点后，再统一暂停。这是一种协作式中断，确保了操作的安全性。

（此题答案与第6题“JVM性能调优的常用参数有哪些？”核心内容重合，可参考该题答案。）

### 6. JVM 高级话题

#### 6.1 即时编译 (JIT)

##### 1. 什么是即时编译（JIT）？ ★★★★★

即时编译（Just-In-Time Compilation, JIT）是HotSpot虚拟机中一项核心的性能优化技术。

Java程序最初是通过**解释器**逐行解释执行字节码的，效率较低。JIT编译器会在程序**运行时**，动态地识别出那些被频繁执行的**“热点代码”**，然后将这些字节码**编译成本地机器码**并缓存起来。当下次再执行这些代码时，就会直接运行编译好的机器码，从而极大地提升了执行效率。

##### 2. 什么是AOT编译？和JIT有啥区别？ ★★★★☆

- **AOT（Ahead-of-Time）编译**：指在程序**运行之前**，就将全部或部分字节码直接编译成本地机器码。

- 区别：

  | 特性 | JIT (即时编译) | AOT (提前编译) |
  | :--- | :--- | :--- |
  | 编译时机 | 运行时动态编译 | 运行前静态编译 |
  | 优化依据 | 基于程序运行时的真实剖面信息，优化更精准 | 只能进行静态分析和猜测，优化受限 |
  | 启动速度 | 启动时需要解释执行，较慢 | 启动时直接运行机器码，启动快 |
  | 性能峰值 | 需要预热，但能达到更高的性能峰值 | 无需预热，但性能峰值通常低于JIT |

##### 3. JIT编译器是如何识别“热点代码”的？ ★★★★☆

HotSpot虚拟机使用**热点探测（Hot Spot Detection）**技术，主要有两种方式：

1. **基于采样（Sampling-based）**：周期性地检查各个线程的栈顶，如果发现某个方法经常出现在栈顶，就认为它是热点方法。
2. **基于计数器（Counter-based）**：为每个方法（或代码块）设置一个计数器，统计其执行次数。当计数器超过一个阈值时，就认为它是热点。HotSpot主要使用这种方式。计数器分为两种：
   - **方法调用计数器**：统计方法被调用的次数。
   - **回边计数器**：统计方法中循环体代码执行的次数。

##### 4. Java的执行模式是怎样的？ ★★★☆☆

Java采用的是**解释执行**和**编译执行**相结合的**混合模式（Mixed Mode）**。

- **解释执行**：在程序启动时，解释器首先发挥作用，使得程序能够快速启动和响应。

- 编译执行：随着程序的运行，JIT编译器会逐渐介入，将热点代码编译成本地机器码，以获取更高的执行性能。

  这是HotSpot虚拟机的默认模式，也是性能最好的模式。

##### 5. JVM如何实现方法内联优化？ ★★★★☆

方法内联（Method Inlining）是JIT最重要的一种优化手段。

- **原理**：在编译期间，将一个方法调用的地方，直接用该**方法体的内容进行替换**，从而消除方法调用的开销（如创建栈帧、参数传递等）。
- **实现**：JIT会根据方法的大小、调用频率等因素来决定是否进行内联。方法内联后，还能为其他优化（如逃逸分析、冗余代码消除）创造更好的条件。

##### 6. 简单介绍一下JIT优化技术？ ★★★☆☆

除了方法内联，JIT还包含众多优化技术，例如：

1. **公共子表达式消除**：如果一个表达式重复出现，并且其值没有改变，编译器会将其计算结果保存起来，后续直接使用。
2. **数组边界检查消除**：如果编译器能确定一个数组访问肯定不会越界（例如在循环中），就会消除运行时的边界检查。
3. **逃逸分析**：分析对象的作用域，如果一个对象不会“逃逸”出方法外部，就可能在栈上分配，或者被标量替换。

##### 7. JVM中的即时编译器有哪些？ ★★★☆☆

在HotSpot中，主要包含两种JIT编译器：

1. **C1编译器（Client Compiler）**：注重**启动速度**和**编译速度**。它进行的优化比较简单，主要用于客户端应用或服务启动初期。

2. C2编译器（Server Compiler）：注重性能峰值。它会进行更深入、更复杂的优化，编译耗时较长，但生成的代码执行效率非常高。主要用于服务端应用。

   在JDK 8及以后，默认开启分层编译（Tiered Compilation），C1和C2会协同工作，以兼顾启动速度和长期性能。

#### 6.2 其他高级优化

##### 1. JVM中的逃逸分析是什么？ ★★★☆☆

逃逸分析（Escape Analysis）是JIT的一项优化技术。它分析一个**对象动态作用域**，判断这个对象是否有可能被方法外部的线程或代码所访问。

- **不逃逸**：如果对象只在方法内部使用，JIT就可能进行优化：
  - **栈上分配**：直接在栈上为对象分配内存，方法结束时随栈帧销毁，无需GC。
  - **标量替换**：将对象拆解成多个基本类型的成员变量，直接在栈上分配。
  - **锁消除**：如果一个锁对象不逃逸，JIT会消除这个不必要的锁。

##### 2. JVM如何进行代码缓存管理？ ★★★☆☆

代码缓存（Code Cache）是用于存放**JIT编译后的本地机器码**的一块内存区域。

- 这块区域的大小是固定的，可以通过`-XX:ReservedCodeCacheSize`设置。
- 如果代码缓存被占满，JIT编译器会停止工作，程序将退化回解释执行模式，导致性能下降。
- 在支持分层编译的JVM中，代码缓存也会被划分为不同区域，用于存放不同层级编译后的代码。

##### 3. JVM如何保证对象分配内存过程的线程安全？ ★★★★☆

在并发环境下，多个线程可能同时请求分配内存，JVM通过两种方式来保证分配过程的线程安全：

1. **CAS + 失败重试**：对在堆上分配内存的操作，使用CAS指令配合自旋的方式来保证原子性。
2. **本地线程分配缓冲（TLAB, Thread Local Allocation Buffer）**：这是**更常用**的方式。JVM会为每个新创建的线程在**新生代的Eden区**预先分配一小块私有内存。线程分配对象时，会**优先在自己的TLAB中分配**，因为是私有区域，所以无需加锁。只有当TLAB用完需要重新分配时，才需要使用CAS进行同步。

### 7. JVM 异常与错误

#### 7.1 常见错误类型

##### 1. JVM常见的错误类型有哪些？ ★★★☆☆

JVM中，所有异常和错误的顶级父类是`java.lang.Throwable`，它有两个主要子类：

1. **`Error` (错误)**：表示程序无法处理的严重问题，通常会导致程序终止。例如`OutOfMemoryError`, `StackOverflowError`。
2. **`Exception` (异常)**：表示程序可以处理的异常情况。又分为：
   - **受检异常 (Checked Exception)**：编译期强制要求处理的异常（如`IOException`）。
   - **非受检异常 (Unchecked Exception) / 运行时异常 (RuntimeException)**：可以不显式处理的异常（如`NullPointerException`）。

##### 2. 什么是StackOverflowError？ ★★★☆☆

`StackOverflowError`（栈溢出错误）表示一个线程请求的**栈深度**超过了虚拟机所允许的最大深度。

- **常见原因**：
  - **无限递归**或过深的函数调用。
  - 方法中定义了大量的局部变量。

##### 3. 什么是OutOfMemoryError？和StackOverflowError的区别是什么？ ★★★★☆

- **`OutOfMemoryError` (OOM)**：内存溢出错误，指JVM在尝试为新对象分配内存时，堆或方法区等内存区域**没有足够的空间**，并且在GC之后也无法获得。

- 区别：

  | 特性 | StackOverflowError | OutOfMemoryError |
  | :--- | :--- | :--- |
  | 发生区域 | 虚拟机栈 | 堆、方法区等 |
  | 核心原因 | 栈深度过大 | 内存空间不足 |
  | 表现 | 递归太深，一个线程耗尽栈空间 | 创建对象太多，所有线程耗尽堆空间 |

##### 4. 什么是ClassNotFoundException？ ★★★☆☆

`ClassNotFoundException`是一个**受检异常**。它发生在**运行时**，当程序尝试通过**反射**（如`Class.forName()`）或类加载器的`loadClass()`方法来**动态加载**一个类，但在类路径（Classpath）下**找不到**对应的`.class`文件时抛出。

##### 5. 什么是NoClassDefFoundError？它与ClassNotFoundException有什么区别？ ★★★★☆

- **`NoClassDefFoundError`**：是一个**错误（`Error`）**。它发生在JVM在**链接**阶段（或首次主动使用时），发现一个类在**编译时存在**，但在**运行时**却找不到了。

- 区别：

  | 特性 | ClassNotFoundException | NoClassDefFoundError |
  | :--- | :--- | :--- |
  | 类型 | Exception (受检异常) | Error |
  | 触发时机 | 动态加载时（如反射） | 静态链接或首次使用时 |
  | 原因 | 类路径下确实没有这个类 | 编译时有，运行时没了。常见原因是jar包冲突或部署遗漏 |
  | 场景 | 手动调用Class.forName()等 | 依赖的类在运行时不可用 |

##### 6. 什么是PermGen/Metaspace溢出？ ★★★★☆

这是`OutOfMemoryError`的一种具体类型，指**方法区**的内存耗尽。

- **JDK 1.7及以前（PermGen）**：永久代溢出。原因是加载的类、字符串常量池等占满了固定的永久代空间。
- **JDK 1.8及以后（Metaspace）**：元空间溢出。原因是加载的类信息占满了分配的元空间内存（默认情况下只受限于物理内存）。
- **主要原因**：运行时动态生成大量类（如CGLIB）、加载了过多的类库。

##### 7. 内存泄漏和内存溢出的区别是什么？ ★★★★☆

- **内存泄漏（Memory Leak）**：指程序中一些**不再使用**的对象，由于仍然被某些活动的引用所持有，导致**垃圾回收器无法回收**它们。
- **内存溢出（Memory Overflow / OutOfMemoryError）**：指程序在申请内存时，没有足够的内存空间供其使用。
- **关系**：**持续的内存泄漏最终会导致内存溢出**。

##### 8. 如何排查JVM的内存泄漏？ ★★★☆☆

1. **生成堆转储快照（Heap Dump）**：使用`jmap`命令或通过监控工具在OOM时自动生成`.hprof`文件。
2. **分析快照文件**：使用**MAT (Memory Analyzer Tool)** 或`VisualVM`等工具打开快照。
3. **定位泄漏源**：
   - 查看**支配树（Dominator Tree）**，找到占用内存最多的“巨无霸”对象。
   - 使用MAT的“Leak Suspects”报告，它会自动分析并给出可能的泄漏点。
   - 分析对象的引用链，找到是哪个GC Root导致了无用对象无法被回收。

##### 9. JVM中的“死锁”是如何发生的？ ★★★★☆

JVM中的线程死锁与操作系统中的概念一致，指两个或多个线程因争夺资源而造成互相等待的现象。通常由不正确的**锁使用顺序**导致。

- **例子**：线程A持有锁1，然后尝试获取锁2；同时线程B持有锁2，尝试获取锁1。两个线程就会无限期地互相等待对方释放锁。
- **排查**：使用`jstack <pid>`命令，`jstack`会自动检测并报告死锁信息，清晰地指出哪个线程在等待哪个锁。

##### 10. JVM发生OOM一定会导致JVM退出吗？ ★★★☆☆

**不一定**。当某个线程抛出`OutOfMemoryError`时，该线程会终止，但只要进程中还有其他**非守护线程**在运行，JVM就不会退出。

##### 11. 什么情况会导致JVM退出？ ★★★☆☆

1. **所有非守护线程都已终止**。
2. 程序中调用了`System.exit()`方法。
3. 发生了JVM无法处理的致命错误（如操作系统错误、JVM自身bug）。
4. 在操作系统层面被强制杀死（如`kill -9`）。

##### 12. 对JDK进程执行kill -9有什么影响？ ★★★★☆

`kill -9 <pid>`是一个由操作系统发出的**强制杀死进程**的信号。

- 它会**立即终止**JVM进程，不给JVM任何机会执行善后工作。
- **影响**：
  - JVM的**Shutdown Hook（关闭钩子）**不会被执行。
  - 内存中的数据会全部丢失，不会写入磁盘。
  - 可能导致文件句柄、网络连接等资源未被正常关闭。
- **对比**：`kill <pid>`（或`kill -15`）是发送一个“终止”信号，JVM可以捕获这个信号并执行优雅的关闭流程。除非程序无响应，否则应优先使用`kill`而非`kill -9`。

### 8. 新增补充问题

#### 8.1 深入理解JVM特性

##### 1. JVM的内存屏障是什么？它在并发编程中有什么作用？ ★★★★☆

- **是什么**：内存屏障（Memory Barrier），也叫内存栅栏，是一条CPU指令。
- **作用**：它在并发编程中主要有两个作用：
  1. **禁止指令重排序**：确保屏障前后的指令不会被编译器或处理器为了优化而随意交换执行顺序。
  2. **保证可见性**：强制将CPU缓存中的数据刷新回主内存（写屏障），或者强制使CPU缓存失效并从主内存重新加载数据（读屏障）。`volatile`关键字的底层实现就依赖于内存屏障。

##### 2. 对象在JVM内存中的布局是怎样的？（对象头、实例数据、对齐填充） ★★★★☆

在HotSpot虚拟机中，一个Java对象在内存中的布局分为三个部分：

1. **对象头（Header）**：
   - **Mark Word**：存储对象自身的运行时数据，如哈希码、GC分代年龄、锁状态标志、线程持有的锁等。
   - **类型指针（Class Pointer）**：指向该对象的类元数据（`Klass`对象）的指针，JVM通过它来确定这个对象是哪个类的实例。
   - **数组长度**（如果对象是数组）。
2. **实例数据（Instance Data）**：对象真正存储的有效信息，即程序代码中定义的各种字段内容。
3. **对齐填充（Padding）**：可选部分。为了保证对象的大小是8字节的整数倍，可能会有这部分填充字节，它不是必需的，仅仅起着占位符的作用。

##### 3. 栈帧的结构是怎样的？（局部变量表、操作数栈、动态链接、方法出口） ★★★★☆

栈帧（Stack Frame）是用于支持虚拟机进行方法调用和方法执行的数据结构，它随着方法调用而创建，随着方法结束而销毁。其主要结构包括：

1. **局部变量表（Local Variable Table）**：存放方法参数和方法内部定义的局部变量。
2. **操作数栈（Operand Stack）**：一个后入先出（LIFO）的栈，用于存放方法执行过程中的操作数和计算结果。
3. **动态链接（Dynamic Linking）**：每个栈帧都包含一个指向运行时常量池中该栈帧所属方法的引用，持有这个引用是为了支持方法调用过程中的动态连接。
4. **方法返回地址（Return Address）**：方法正常退出或异常退出时，需要返回到方法被调用的位置，此区域存放了调用者的程序计数器的值。

##### 4. 线程栈中的本地变量对其他线程可见吗？为什么？ ★★★☆☆

**不可见**。

- **为什么**：因为每个线程都有自己**独立**的Java虚拟机栈，而局部变量是存放在栈帧中的，栈帧又存在于虚拟机栈中。因此，一个线程的局部变量表对其他线程是完全隔离和私有的，不存在数据竞争问题，所以它们是**线程安全**的。

##### 5. Java方法调用时参数是如何传递的（值传递还是引用传递）？ ★★★★☆

Java中**只有值传递（pass by value）**。

- **传递基本数据类型**：传递的是该变量的**值的副本**。在方法内修改这个副本，不会影响到方法外的原始变量。
- **传递对象类型**：传递的是该对象的**引用的副本**（即对象在堆中的内存地址的副本）。虽然是引用的副本，但它和原始引用指向的是**同一个堆中的对象**。
  - 因此，在方法内通过这个引用副本**修改对象的内容（字段）**，会影响到原始对象。
  - 但是，如果在方法内将这个引用副本指向一个**新的对象**，则不会影响到方法外的原始引用。

##### 6. 什么是编译器优化？有哪些常见的编译器优化技术？ ★★★☆☆

- **是什么**：编译器优化是指编译器（包括JIT即时编译器）在不改变程序原有语义的前提下，对代码进行各种等价变换，使其生成更高效的机器码，以提升程序的运行性能。
- **常见技术**：
  1. **方法内联**：将方法调用替换为方法体本身，消除调用开销。
  2. **逃逸分析**：分析对象的作用域，实现栈上分配、锁消除等。
  3. **公共子表达式消除**：复用重复计算的结果。
  4. **数组边界检查消除**：在确定不会越界的情况下，移除运行时的检查。

##### 7. Java中的字节码指令是什么？ ★★★☆☆

字节码指令是Java虚拟机（JVM）的**指令集**。

- `javac`编译器将`.java`源文件编译成`.class`文件，`.class`文件中包含的就是字节码。
- 这些字节码是一种中间形式的、与平台无关的指令，它们不能被CPU直接执行，必须由JVM的解释器解释执行，或者由JIT编译器编译成特定平台的机器码后执行。
- 每条字节码都是一个单字节的操作码（opcode），后面可能跟有操作数。

##### 8. synchronized和volatile在底层JVM是如何通过内存屏障实现的？ ★★★★★

- **`volatile`**：
  - **写操作**：在对`volatile`变量进行写操作的指令之后，会插入一个**Store屏障**。这个屏障会强制将该线程工作内存中的值刷新到主内存，并使其他线程的缓存失效。
  - **读操作**：在对`volatile`变量进行读操作的指令之前，会插入一个**Load屏障**。这个屏障会强制当前线程从主内存重新加载变量的最新值。
- **`synchronized`**：
  - **获取锁（`monitorenter`）**：在进入同步块时，会隐式地执行一个**Load屏障**，清空工作内存，从主内存加载共享变量。
  - **释放锁（`monitorexit`）**：在退出同步块时，会隐式地执行一个**Store屏障**，将工作内存中修改过的共享变量刷新到主内存。

#### 8.2 JVM与其他技术结合

##### 1. JDK中ProcessBuilder和Runtime.exec()的区别是什么？ ★★★☆☆

它们都是用于在Java程序中执行外部命令或进程的工具，但`ProcessBuilder`是更现代、更推荐的选择。

- **`Runtime.exec()`**：是一个便捷但功能有限的老API。它的参数处理、错误流处理和环境配置都比较繁琐和不直观。
- **`ProcessBuilder`**：是一个功能更强大、更灵活的API。它允许在启动进程前，对命令、工作目录、环境变量等进行详细的配置，并且能更方便地重定向标准输入、输出和错误流。

##### 2. Java Agent是什么？它有什么应用场景？ ★★★★☆

- **是什么**：Java Agent是一种特殊的jar包，它利用**Java Instrumentation API**，可以在**JVM启动时或运行时**，动态地修改已加载或未加载的类的字节码，从而在不修改源代码的情况下，为应用程序增加额外的功能。
- **应用场景**：
  1. **APM（应用性能监控）**：如SkyWalking, Pinpoint等，通过Agent在方法入口和出口插入代码，来实现对方法耗时、调用链、SQL执行等的监控。
  2. **热部署**：在不重启服务的情况下，动态更新类的实现。
  3. **代码覆盖率分析**：在测试时动态地为代码插桩，以统计代码执行情况。

##### 3. 什么是Java Flight Recorder (JFR) 和 Java Mission Control (JMC)？它们用于什么？ ★★★☆☆

它们是Oracle官方提供的一对强大的、低开销的性能监控和诊断工具。

- **JFR (Java Flight Recorder)**：是一个内置于HotSpot虚拟机的**事件记录引擎**。它能以极低的性能开销（通常<1%），持续收集关于JVM运行、Java应用和操作系统的详细数据，并将这些数据记录到一个`.jfr`文件中。
- **JMC (Java Mission Control)**：是一个用于**分析JFR记录文件**的可视化工具。它能以图表和表格的形式，直观地展示应用程序的性能瓶颈，如热点方法、GC活动、锁竞争、内存泄漏等，是进行事后问题诊断的利器。

##### 4. JVM如何与操作系统进行交互？ ★★★☆☆

JVM作为一个应用程序，运行在操作系统之上，它通过以下几种主要方式与操作系统交互：

1. **内存管理**：JVM向操作系统申请一块大的内存（堆、元空间等），然后自己进行精细化的管理。
2. **线程调度**：Java的平台线程与操作系统的内核线程是对应的。JVM依赖操作系统的线程调度器来分配CPU时间片。
3. **文件系统**：通过调用操作系统的API来进行文件的读写操作。
4. **网络通信**：通过调用操作系统的Socket API来进行网络数据的收发。
5. **本地方法接口（JNI）**：允许Java代码调用由其他语言（如C/C++）编写的、直接与操作系统交互的本地库函数。
